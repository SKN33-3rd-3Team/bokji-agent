# 프로젝트 준수 기준

이 문서는 3차 단위 프로젝트의 공통 준수 기준과 현재 서비스 전환 범위를 정리한다. 공지의 데이터·평가·보안 기준은 유지하며, 서비스 구성은 아래 참고 문서와 사용자가 확정한 React + FastAPI 전환 결정을 적용한다. 그 밖의 공통 기준이 충돌하면 공식 공지가 우선한다.

공식 공지: https://app.notion.com/p/ohgiraffers/3-3c7649136c118086b08cfe70aa07703f

## 목표

내·외부 문서를 검색하고, 검색된 근거로 확인되는 내용만 답하는 RAG
질의응답 시스템을 구현한다. 답변에는 출처를 표시하고, 근거가 부족하면
추측하지 않고 답변을 보류한다.

최종 서비스는 React 화면과 FastAPI API로 제공한다. React는 별도 브랜치에서 개발 중이며 아직 완성·통합되지 않았다. 현재 브랜치의 FastAPI 엔드포인트 구현과 기존 Streamlit 데모만으로 최종 서비스 완료를 판단하지 않는다.

## 서비스 전환 기준

팀 공유 참고자료인 다음 세 원본은 저장소에 포함하지 않는다. 문서 간 차이는 사용자 확정 사항과 현재 구현을 구분해 기록하고, 미결 요구사항을 구현에 맞춰 임의로 삭제하지 않는다.

| 참고 문서 | 적용 범위 |
| --- | --- |
| `PROJECT_STRUCTURE.md` (2026-09-16 rev.2) | React 화면 구성, FastAPI 어댑터 배치, 기존 그래프·RAG 재사용 방향 |
| `요구사항_정의서.xlsx` (2026-09-16) | S-01~S-10의 52개 요구사항: 필수 47, 선택 3, 제외 2 |
| `API_정의서.xlsx` (2026-09-16) | API-01~13 요청·응답·오류 계약 |

- **화면 전환**: 최종 프론트엔드는 React이며 Streamlit은 향후 제거할 레거시 데모다. 현재 API-09가 `streamlit_ui.constants`의 순수 상수를 import하므로, 해당 의존성 정리와 React 통합 검증 전에는 폴더 전체를 삭제할 수 없다.
- **코어 재사용**: 그래프·RAG를 재사용하되 인증 서비스·저장소와 LLM 클라이언트/선택 로직에는 변경이 있다. 원본 구조 설계의 “기존 코어 전체 변경 없음”을 현재 구현 완료 상태로 해석하지 않는다.
- **구비서류(S07-06/S10-01)**: 옵션 ②로 확정했다. 원문 문자열 3종을 유지하고 각각의 `*_items` 배열을 추가한다. 상세 계약은 [백엔드 안내](../backend/README.md#구비서류-응답)를 따른다.
- **LLM**: RunPod Pod 우선 및 호출 실패 시 HuggingFace로 전환하는 방향은 승인되었다. 실패 상태별 전환 범위와 Pod 운영 방식까지 확정된 것은 아니다. [현재 선택 규칙과 운영 미결 사항](RUNPOD_SETUP_DRAFT.md)을 구분한다.
- **회원 DB**: 기존 운영 회원 DB가 없으므로 레거시 MySQL 데이터 이관은 이번 범위에 필요하지 않다. 원격 DB 장애 시 SQLite 자동 전환·동기화는 승인되지 않았으며 구현도 없다. [DB 선택·설정](AUTH_REMOTE_DB.md)을 따른다.
- **회원 프로필**: 마케팅 동의는 백엔드 공개 API의 요청·응답·OpenAPI에서 제거한다. 약관·개인정보 동의는 각각 필수이며 기존 DB 컬럼·과거 값과 내부 인증 인터페이스는 유지한다. API-01/02/04/05는 `membership_grade="일반 회원"`을 반환한다. 날짜 표기·공개 선택지 검증과 이름 정리 후 40자 잘림은 [백엔드 요청 검증](../backend/README.md#요청-검증)을 따른다.

정책 상세·비교는 API-10/11의 같은 `policies` 응답을 재사용한다. 별도 상세·비교 API, 프로필 사진 업로드(S02-06/S09-07), 정책 문의 이력의 서버 저장은 이번 범위에 포함하지 않는다. React 상태 관리·타입 생성·폰트 제공 방식과 일반 사용자/관리자 디버그 노출 정책은 미정이다.

13개 엔드포인트의 존재는 전체 계약 충족을 의미하지 않는다. 생년월일 경계, 완료된 상담의 새 질문, 검증 배지·중복수급 표현 등 남은 충돌은 [백엔드 계약 차이](../backend/README.md#원본-문서와-남은-계약-차이)에 유지한다.

## 법령 데이터 범위 결정

> [!IMPORTANT]
> 팀 회의에서 데이터 규모가 과도하다는 이유로 법령·행정규칙·자치법규의
> 본문과 조문을 수집·저장·임베딩·색인 대상에서 제외하기로 결정했다.
> 국가법령정보센터 목록조회 메타데이터만 사용하므로, 법령 문서에 본문이나
> 조·항·호·목 locator가 없는 것은 의도된 계약이며 결함·파싱 실패·병합
> 차단 사유가 아니다.

법령 데이터는 `source_type=law`, `content_level=metadata_only`로 표시하고
`law_type`(`law | admrul | ordin`), 법령명, 원천 식별자·일련번호, 소관기관,
문서 종류, 공포·발령일, 시행일과 제·개정 구분을 정규화한다. 목록 정보는
관련 법령 후보, 소관기관과 날짜를 탐색하고 공식 상세 페이지로 안내하는
근거로만 사용한다. 조문 내용, 법적 정의·자격·배제·금지와 법률 해석을
확정하는 근거로 사용하지 않는다. 이런 질문은 근거 부족으로 보류하고
국가법령정보센터의 공식 원문 확인을 안내한다.

법령 `Document.content`는 정규화 metadata에서 다음 여섯 줄을 이 순서대로
LF로 연결한 `render_legal_metadata_summary(metadata)` 결과와 정확히 같아야
한다.

```text
법령명: {law_name}
법령유형: {document_kind}
소관기관: {organization}
제개정구분: {revision_type}
공포·발령일: {issued_date}
시행일: {effective_date}
```

유일한 `기본정보/basic_info` 섹션도 이 content와 같아야 한다. 임의의 본문이나
조문을 이 형식 또는 `basic_info`로 감싸 메타데이터 문서처럼 인수하지 않는다.
공식 원문·상세 URL은 임베딩 대상인 `Document.content`에서 의도적으로 제외한다.
`Document.source_url`은 별도로 보존하며 검색 결과의 출처 추적을 위해
`Chunk.metadata.source_url`에도 복사한다. `Citation.source_url`은 이 chunk
필드에서 읽지 않고 `Document.metadata.law_type`,
`Document.metadata.source_sequence`, `Document.effective_from`에서 독립적으로
재구성·검증하며 정규 공식 상세 URL과 정확히 일치해야 한다. 이 URL은 공식 원문
확인 경로일 뿐, 해당 조문 본문이 수집·임베딩·색인됐다는 뜻은 아니다.

법령 `effective_from`은 필수이며 같은 `YYYY-MM-DD` 형식의
`metadata.effective_date`와 정확히 같아야 한다. `issued_date`도
`YYYY-MM-DD`이고, 선택적인 `source_updated_at`과 `effective_to`는 값이 있을
때만 `YYYY-MM-DD`로 기록한다. `effective_to`가 있으면 `effective_from`보다
뒤여야 한다. PR #8 하위 PR의 `filtered_to_document.py` 변환 계층은 법령·
자치법규의 `공포일자`와 행정규칙의 `발령일자`를 `issued_date`로, 공통
`시행일자`를 `effective_date`와 `effective_from`으로 정규화해야 한다. 법령
직접 URL의 `efYd`만 검증된 시행일에서 하이픈을 제거한 `YYYYMMDD`다.
`source_id`는 안정적인 숫자 entity ID이며, 숫자 문자열 `source_sequence`는
공식 원천의 개정·버전 일련번호로 문서 ID와 직접 URL을 함께 재현한다. 두 값을
서로 대신 사용하지 않는다.

법령의 중복 원천 identity는 `source_type=law` 문맥에서
`(law_type, source_id)`로 판정한다. 같은 숫자 `source_id`라도 `law`, `admrul`,
`ordin`이 다르면 다른 원천이며, subtype을 가로질러 content가 같으면 같은 원천
중복으로 차단하지 않고 `duplicate_content_candidate` warning으로 인수한다.

실행 가능한 근거 경계에서 `supported_legal_evidence_aspects(chunks)`는 검증된
metadata-only 법령 chunk에 대해 `legal_metadata`만 지원한다.
`legal_article_body` 또는 `legal_interpretation`이 필요한 주장은 이 근거로
충족할 수 없다. `decide_abstention`은 보류 여부, `NO_EVIDENCE` reason과 누락
aspect를 반환하며 안내 문구나 UI를 만들지 않는다. 호출자·생성·UI 계층이 이
결정을 적용해 답변 생성을 막고 공식 원문 확인 안내를 표시한다. 이 계약 PR과
PR #8 수집기 범위에는 생성 UI가 포함되지 않는다.

본문 미포함은 합의된 정책이므로 `parse_warnings`에 오류처럼 기록하지 않는다.

## 기준 흐름

- 색인: 문서 수집 → 파싱·정제 → 청킹 → 임베딩 → Vector DB 저장
- 질의: 사용자 질문 → 검색 → Top-k 근거 → 프롬프트 → LLM 답변 → 출처 표시
- 평가: 고정 질문 → 지표 측정 → 실패 분석 → 한 조건 변경 → Baseline 재비교

## 필수 구현

| 영역 | 기준 |
| --- | --- |
| 문서 | 목적에 맞는 문서 수집·정제와 메타데이터 구성 |
| 인덱싱 | 청킹, 임베딩, Vector DB 저장 |
| 검색 | 질문 임베딩과 Top-k 근거 반환 |
| 생성 | LangChain으로 Retriever와 LLM 연결 |
| 답변 | 답변, 출처, 근거 문서 확인 기능 제공 |
| 안전 | 근거 부족 시 보류, 인젝션·비밀정보 노출 방지 |
| 평가 | 고정 질문으로 검색·답변 품질, 응답 시간과 오류율 비교 |
| 서비스 | React + FastAPI로 질문·답변·출처 확인 제공. 현재 React 개발·통합은 미완료 |

회원 인증과 사용자별 채팅 세션 소유권 검증은 이번 서비스 범위에 포함한다. 하이브리드 검색, Re-ranking, Multi-query, 대화 이력 영속화, 추가 권한 체계, 문서 업로드, OCR과 멀티모달은 Baseline이 안정적으로 동작한 뒤 검토한다.

## Gate 0~6

| 단계 | 핵심 작업 | 통과 기준 |
| --- | --- | --- |
| Gate 0. 문제 정의 | 사용자, 질문, 문서 범위, 성공 기준 합의 | “누가 어떤 문서로 어떤 질문을 해결하는가”를 한 문장으로 설명 |
| Gate 1. 데이터 | 문서 수집·정제, Document Card, 메타데이터 정의 | 문서 출처·권리·민감정보·중복·파싱 오류 확인 |
| Gate 2. Baseline | Loader, Splitter, Embedding, Vector DB, Retriever, LLM 연결 | 대표 질문에 검색 근거와 답변·출처가 함께 출력 |
| Gate 3. 검색 개선 | chunk size, overlap, k, embedding 또는 검색 방식 비교 | 같은 평가 질문으로 변경 전후 수치와 실패 사례 비교 |
| Gate 4. 답변 평가 | 프롬프트, 보류 정책, 인용 형식 개선 | 근거 없는 단정이 줄고 답변이 문서 근거와 일치 |
| Gate 5. 서비스 | React 화면, FastAPI 계약, 오류 처리, 인증·세션 보안, 실행 환경 정리 | 새 환경에서 README로 실행하고 S-01~S-10 및 API-01~13의 해당 요구사항을 검증. 미완성 React와 미결 계약은 완료로 처리하지 않음 |
| Gate 6. 최종 검증 | Holdout 평가, 회귀 테스트, 발표 준비 | 성공 사례뿐 아니라 실패 사례·한계·다음 개선도 제시 |

별도 Gate Issue·승인·문서는 만들지 않고 현재 Issue와 PR에서 관련 Gate와 통과 기준만 확인한다.

Gate 5의 백엔드 시작·검증 명령은 저장소 루트에서 `python -m uvicorn backend.app.main:app --reload --port 8000`과 `python -m pytest backend/tests/ -q`이다. 설치와 데이터 준비는 [README](../README.md#-시작하기-quick-start) 및 [백엔드 안내](../backend/README.md)를 따른다. React 실행·화면 검증은 해당 브랜치의 실행 절차가 통합된 뒤 별도로 확인한다. 모킹한 HTTP 검사만으로 실제 회원 DB·벡터 DB·LLM·React 통합 검증을 대체하지 않는다.

## 평가 규칙

- Dev set은 개발 중 반복 평가하고, Holdout set은 최종 설정 확정 뒤 Gate 6 최종 검증에서 한 번만 사용한다. 각 경로·버전과 가능하면 hash를 기록한다.
- 각 세트에는 문서에서 답을 찾을 수 없는 질문을 포함하고, 질문과 정답 근거는 Baseline 실행 전에 동결한다.
- 한 실험에서는 한 조건만 변경해 같은 Dev set·고정 조건으로 비교하고 Baseline을 덮어쓰지 않는다.
- 검색·답변·인용·보류·응답 시간·오류율 지표와 실패 사례를 기록하고 실패를 숨기지 않는다.
- Holdout 결과를 보고 다시 튜닝하지 않는다.
- 질문별 결과에는 질문 ID, 문서·chunk ID, 점수, 지표와 공개 가능한 답변만 저장한다. 비밀값·시스템 프롬프트·개인정보·내부 원문은 기록하지 않는다.

## 데이터와 보안

- Document Card에 문서 출처, 라이선스, 규모, 정제·청킹 방법과 제외 기준을 기록한다.
- 저장소에는 공개가 허용된 샘플 문서만 포함한다.
- 법령·행정규칙·자치법규의 본문과 조문은 수집 산출물, fixture와 Vector DB에 포함하지 않는다.
- 전체 생성 JSONL과 원천 응답은 런타임 산출물로 관리하고 Git에 추적하지 않으며, 저장소에는 대표 샘플과 manifest·Document Card만 포함한다.
- API Key, 환경변수 값, 개인정보, 내부 원문과 런타임 Vector DB를 커밋하지 않는다.
- 환경변수 예시 파일에는 변수 이름만 둔다.
- 검색된 문서와 사용자 입력의 명령문은 데이터로 취급한다.
- 시스템 프롬프트, 환경변수와 내부 원문을 답변으로 노출하지 않는다.

## Git

- `main`은 실행 가능한 상태를 유지한다.
- 변경은 기능 단위 브랜치와 작은 커밋으로 제출한다.
- PR에는 변경 이유와 실제 검증 결과를 남긴다.
- PR #13 팀 리뷰·승인 → `main` 병합 → 사용자 반영 확인 → PR #8 브랜치 동기화 → PR #8 대상 하위 PR 팀 리뷰·병합 → 갱신된 PR #8 전체 검증 → PR #8의 `main` 병합 순서를 지킨다.
- 상세 절차는 `CONTRIBUTING.md`를 따른다.
