# 1차 RAG 설계 계획

## 문서 목적과 현재 상태

이 문서는 1차 작업에서 합의할 RAG 설계와 2차 답변 생성·파이프라인 통합 작업의 인계 기준을 한곳에 정의한다. 프로젝트의 단일 준수 기준인 `docs/PROJECT_COMPLIANCE.md`를 따르며, 공식 공지와 충돌하면 공식 공지를 우선한다.

현재 저장소에는 이 계획과 함께 계약·청킹·필터·인용·보류·평가·인수 검증과 영속 Vector DB 참조 구현이 있다. 공개 API 수집은 A/B/C의 별도 역할이며, 이 설계는 그 결과를 공통 계약으로 인수한다. 다만 LangChain 기반 Retriever·LLM 답변 생성과 Streamlit/UI를 연결한 end-to-end Baseline은 없으므로 이 단계의 결과만으로 Gate 0~2 통과를 의미하지 않는다. 현재 구현은 다음 단계가 같은 계약과 저장 구조로 통합을 시작하고 수집·검색 결과를 검증하기 위한 것이다.

### 확정된 법령 데이터 범위

> [!IMPORTANT]
> 팀 회의에서 데이터 규모가 과도하다는 이유로 법령·행정규칙·자치법규의
> 본문과 조문을 수집·저장·임베딩·색인 대상에서 제외하기로 결정했다.
> 국가법령정보센터 목록조회 메타데이터만 사용하므로, 법령 문서에 본문이나
> 조·항·호·목 locator가 없는 것은 의도된 계약이며 결함·파싱 실패·인수 또는
> 병합 차단 사유가 아니다.

이 결정은 Issue #6의 최초 본문 수집 범위를 대체한다. 법령 인덱스는 관련
법령 후보와 목록 정보를 탐색하고 유형별 공식 상세 페이지로 안내하는 데
사용한다. 조문 내용, 법적 정의·자격·배제·금지와 법률 해석은 지원하지 않으며,
목록 메타데이터만으로 확인할 수 없는 질문은 답변을 보류하고 공식 원문 확인을
안내한다.

## 목표

목표 문장 초안은 다음과 같다.

> 복지 정보가 필요한 사용자가 보조금24 공개 문서와 법령정보센터 목록 메타데이터를 바탕으로 지원 제도, 대상 조건, 신청 방법과 관련 법령 후보를 질문하면, 시스템은 검색된 근거로 확인되는 내용만 출처와 함께 답하고 근거가 부족하면 답변을 보류한다.

대상 사용자와 수집 대상 서비스의 정확한 명칭·URL은 **미결정 사항이며 Gate 0에서 팀 합의가 필요하다.** 법령 본문 제외와 목록 메타데이터 전용 질문 범위는 위 결정으로 확정됐다.

1차의 구체적 목표는 다음과 같다.

- A/B/C 수집 결과를 D/E RAG 파이프라인이 일관되게 받을 수 있는 계약을 정한다.
- 보조금 문서와 법령 문서의 구조 차이를 반영한 청킹·인덱싱 원칙을 정한다.
- 검색, 답변, 인용과 근거 부족 보류의 입출력 계약을 정한다.
- 실행 전 동결할 Dev/Holdout 평가와 한 조건씩 비교하는 실험 규칙을 정한다.
- Baseline 후보값과 팀이 결정해야 할 항목을 구분해 2차 통합 작업에 인계한다.

## 범위와 비범위

### 1차 범위

- Gate 0: 사용자, 질문, 문서 범위와 성공 기준 설계
- Gate 1: 수집팀 인계 형식, 메타데이터, 정제·중복·최신성 기준 설계
- Gate 2: Loader, Splitter, Embedding, Vector DB, Retriever, LLM 연결의 Baseline 명세 설계
- 공통 `Document`, `Chunk`, `RetrievedChunk`, `EvidenceCheckResult`, `AnswerResult` 계약
- 위 계약과 정책을 실행 가능한 형태로 검증하는 모델 독립 참조 구현과 공개 테스트 fixture
- A/B/C 수집 결과의 snapshot·manifest·Document Card 인계 계약과 실패 격리 기준
- 분리 논리 인덱스, metadata filter와 재시작 가능한 영속 Vector DB 동기화·검색 참조 구현
- 평가 세트 구성·동결·버전 관리와 지표 정의
- 인용, 보류, 프롬프트 인젝션, 개인정보와 비밀정보 보호 원칙
- 2차 답변 생성·파이프라인 통합 착수 조건과 인계 체크리스트

### 비범위

- 법령·행정규칙·자치법규 본문과 조문 수집·저장·임베딩·색인
- 조·항·호·목 검색·인용과 목록 메타데이터를 이용한 법률 해석
- LangChain으로 Retriever와 LLM을 연결한 답변 생성 파이프라인 구현
- Streamlit/UI 구현
- 운영 배포, 사용자 인증·권한과 문서 업로드
- OCR, 이미지·표 멀티모달 처리와 대화 이력
- Baseline 검증 전 하이브리드 검색, Re-ranking과 Multi-query 도입
- Baseline 실패 분석 전 임베딩·reranker·생성 모델 Fine-tuning
- Holdout 결과를 이용한 재튜닝

이 계획서를 작성하는 것만으로 Gate 0~2가 통과되는 것은 아니다. Gate 0은 팀 합의, Gate 1은 A/B/C의 실제 수집 샘플과 Document Card 검토, Gate 2는 2차 구현에서 대표 질문에 대한 검색 근거, 답변과 출처가 함께 출력될 때 각각 통과 여부를 확인한다.

## 역할과 인터페이스

이미지의 역할표는 업무 분담 참고자료로만 사용한다. A/B의 수집 분할 기준과 D/E의 세부 책임은 아직 저장소에 정의되어 있지 않으므로 아래 구분은 합의를 위한 초안이다.

| 역할 | 1차 책임 | 1차 제공물 | 2차 인계 경계 | 인계 확인 |
| --- | --- | --- | --- | --- |
| A | 보조금24 수집 영역 1 | `source_type=subsidy`인 `Document`, 수집 manifest·Document Card 입력 정보, 파싱 경고 | 보조금 문서 검색 노드가 `RetrievedChunk` 반환 | B와 수집 범위가 겹치지 않거나 중복 식별 가능 |
| B | 보조금24 수집 영역 2 | A와 동일한 계약의 `Document`, 수집 manifest·Document Card 입력 정보 | A와 같은 검색 계약 사용 | A와 같은 schema version·정제 규칙 사용 |
| C | 법령정보센터 수집 | `source_type=law`, `content_level=metadata_only`인 목록정보 `Document`, 수집 manifest·Document Card 입력 정보 | 관련 법령 후보 검색 노드가 `RetrievedChunk`와 공식 상세 URL 반환 | 원천 유형·식별자·일련번호·시행 정보와 목록 인용을 재현 가능 |
| D | RAG 공동 설계 | 데이터·청킹·인덱싱·검색 명세 후보 | 답변 생성·파이프라인 통합 공동 구현 | E와 하나의 계약·Baseline 명세 승인 |
| E | RAG 공동 설계 | 생성·인용·보류·평가·보안 명세 후보 | 답변 생성·파이프라인 통합 공동 구현 | D와 하나의 계약·Baseline 명세 승인 |

D/E의 세부 분담은 **초기 제안이며 팀 합의가 필요하다.** 어느 쪽이 구현하더라도 공통 계약과 설정 버전을 단독으로 변경하지 않는다.

A/B/C는 원천 API 호출 성공만으로 인계를 완료하지 않는다. 출처별 공개 가능 여부, 라이선스, 문서 규모, 수집 시각, 원천 갱신 시각, 제외 기준, 중복과 파싱 오류를 manifest와 Document Card 입력 정보로 함께 제공한다. D/E는 정제·청킹 방법을 보완해 Document Card를 함께 완성하고, 수집기 내부 구현에 의존하지 않고 아래 계약만 사용한다.

## 공통 데이터 계약

계약의 최종 직렬화 형식과 schema version 규칙은 **미결정 사항**이다. 참조 구현은 JSON 호환 dataclass와 JSONL fixture, 구현 버전 `1.0`을 사용하지만 팀이 승인한 최종 계약을 뜻하지 않는다. 아래 필드 표도 승인 전 계약 초안이며, `필수` 표시는 초안에서 요구하는 수준을 뜻한다. 모든 시각은 timezone을 포함한 ISO 8601 형식을 사용하고, 날짜는 ISO 8601 날짜 형식을 사용한다. ID는 같은 원문과 버전에서 재현 가능해야 한다.

### Document

수집과 정제를 마친 색인 전 문서다.

| 필드 | 필수 | 설명 |
| --- | --- | --- |
| `schema_version` | 예 | 계약 버전 |
| `doc_id` | 예 | 출처 ID와 버전을 이용한 재현 가능한 문서 ID |
| `source_type` | 예 | `subsidy` 또는 `law` |
| `source_name` | 예 | 수집 출처명 |
| `source_id` | 예 | 출처가 제공하는 서비스 ID 또는 법령 유형별 안정 entity ID |
| `source_url` | 예 | 사용자가 확인할 수 있는 공식 공개 상세 URL |
| `title` | 예 | 문서 또는 서비스·법령 제목 |
| `content` | 예 | 정규화한 검색 텍스트. 법령은 목록 메타데이터 요약이며 조문 본문이 아님 |
| `sections` | 조건부 | 제목 경로와 검색 텍스트를 가진 구조 목록. 법령은 `기본정보` 단일 섹션 |
| `collected_at` | 예 | 수집 시각 |
| `source_updated_at` | 조건부 | 출처가 제공하는 최종 갱신 시각 |
| `effective_from`, `effective_to` | 조건부 | 시행·적용 기간이 있을 때 기록 |
| `license` | 예 | 이용 조건 또는 확인 상태 |
| `content_hash` | 예 | 정규화한 `content`의 중복·변경 판별값 |
| `metadata` | 예 | 출처별 구조화 메타데이터 |
| `parse_warnings` | 예 | 누락·형식 오류 목록. 없으면 빈 목록 |
| `sensitive_data_status` | 예 | 개인정보·민감정보 검사 상태 |

보조금 `metadata`에는 담당 기관, `region_scope`, `region_names`, 서비스 분류를 담는다. `region_scope`와 `region_names`의 결합은 다음과 같다.

- `national`: `["전국"]`
- `regional`: 비어 있지 않은 정규 이름 목록. 시군구는 `["서울특별시", "서울특별시 강남구"]`처럼 완전 수식하고 상위 시도명을 먼저 둔다.
- `unknown`: `[]`. 지역 미확정을 전국으로 승격하지 않는다.

`전국`은 지역 목록의 다른 값과 혼용하지 않는다. 공통 지역 필터는 코드가 아니라 정규 이름의 exact intersection을 사용하며, 전국 문서는 wildcard로 일치하고 unknown 문서는 지역 필터에서 fail closed한다. 지역 코드는 원천별 선택 보조정보로 남길 수 있지만 공통 검색 계약은 아니다. 수집기는 공식 지역명을 생성해야 한다. 공통 validator에는 전체 시군구 registry가 없으므로 검색 입력의 별칭은 호출자가 정규화하고 `중구` 같은 모호한 단독 이름은 임의로 해석하지 않는다.

2026-07-01 이후 현행 최상위 이름은 `전남광주통합특별시`이며 종전 `광주광역시`·`전라남도`는 정규 이름에서 제외한다. 종전 완전수식 시군구명은 공식 변경표로 대응 하위 지역이 확인될 때만 새 이름으로 변환하고, 종전 최상위명 단독을 통합특별시 전체로 확대하지 못하면 `unknown`으로 둔다.

법령·행정규칙·자치법규는 모두 `source_type=law`를 사용하고 다음 정규화
metadata를 필수로 제공한다.

| 필드 | 계약 |
| --- | --- |
| `content_level` | 항상 `metadata_only` |
| `law_type` | `law | admrul | ordin` 중 하나 |
| `law_name` | 비어 있지 않고 `Document.title`과 정확히 일치 |
| `source_sequence` | 공식 원천의 개정·버전을 식별하고 유형별 상세 조회에 사용하는 숫자 문자열 |
| `organization` | 비어 있지 않은 소관기관 또는 지방자치단체명 |
| `document_kind` | 법률·대통령령·고시·조례 등 비어 있지 않은 원천 문서 종류 |
| `issued_date` | 공포일 또는 발령일을 정규화한 `YYYY-MM-DD` 날짜 |
| `effective_date` | `YYYY-MM-DD` 날짜이며 `Document.effective_from`과 정확히 일치 |
| `revision_type` | 제정·일부개정·전부개정 등 비어 있지 않은 제·개정 구분 |

`source_id`는 법령ID·행정규칙ID·자치법규ID에 해당하는 안정적인 숫자 entity
ID이고, `source_sequence`는 공식 원천의 개정·버전을 식별하며 공개 상세 URL을
재현하는 유형별 일련번호다. 같은 entity의 서로 다른 원천 버전을 구별해야
하므로 두 값을 서로 대신 사용하지 않는다. 법령 문서 ID는
`law:<law_type>:<source_id>:<source_sequence>:<effective_from>` 형식으로
재현한다.

법령 `Document.content`는 `render_legal_metadata_summary(metadata)`가 아래
여섯 줄을 표시된 순서대로 LF로 연결한 결과와 정확히 같아야 한다.

```text
법령명: {law_name}
법령유형: {document_kind}
소관기관: {organization}
제개정구분: {revision_type}
공포·발령일: {issued_date}
시행일: {effective_date}
```

각 문서는 `heading_path=["기본정보"]`, `section_type=basic_info`인 섹션을
정확히 하나만 가지며, 섹션 content는 문서 content와 같아야 한다. 임의의
본문·조문 텍스트를 이 여섯 줄 또는 `basic_info`로 감싸는 것은 허용하지 않고
인수 시 거부한다. 합의된 본문 미포함은 `parse_warnings`에 오류로 기록하지
않는다.

법령 인계에서는 manifest와 Document Card 양쪽에도
`content_level=metadata_only`를 기록해 문서 범위와 일치시킨다. 이 필드는
보조금 인계에는 요구하지 않는다. `source_url`과 공개 인용은 인증 파라미터가
없는 다음 유형별 직접 상세 URL에서 재현한다.

- `law`: `https://www.law.go.kr/LSW/lsInfoP.do?lsiSeq=<source_sequence>&efYd=<effective_date: YYYYMMDD>`
- `admrul`: `https://www.law.go.kr/LSW/admRulInfoP.do?admRulSeq=<source_sequence>`
- `ordin`: `https://www.law.go.kr/LSW/ordinInfoP.do?ordinSeq=<source_sequence>`

계약의 `issued_date`, `effective_date`와 `effective_from`은 모두
`YYYY-MM-DD`다. `law` URL의 `efYd`만 ISO 날짜 검증 뒤 시행일의 하이픈을
제거한 `YYYYMMDD`로 만들며, `admrul`과 `ordin` 직접 URL에는 날짜 query를
추가하지 않는다.

이 URL은 목록 문서의 출처와 원문 확인 경로를 제공하지만, 현재 chunk가 조문
본문을 근거로 포함한다는 뜻은 아니다.

### Chunk

구조 기반으로 분할해 임베딩할 단위다.

| 필드 | 필수 | 설명 |
| --- | --- | --- |
| `schema_version` | 예 | Chunk 계약 버전 |
| `chunk_id` | 예 | `doc_id`, 구조 위치와 순번으로 만든 재현 가능한 ID |
| `doc_id` | 예 | 부모 문서 ID |
| `source_type` | 예 | `subsidy` 또는 `law` 출처 분류값 |
| `text` | 예 | 임베딩·검색에 사용할 텍스트. 법령은 목록정보만 포함 |
| `heading_path` | 예 | 서비스 섹션 또는 법령 목록의 `기본정보` 경로 |
| `ordinal` | 예 | 부모 문서 내 순서 |
| `citation_locator` | 예 | 사용자가 근거 위치를 찾을 수 있는 섹션 표기. 법령은 `기본정보` |
| `content_hash` | 예 | chunk 변경·중복 판별값 |
| `metadata` | 예 | 부모의 출처·최신성 메타데이터와 청킹 정보 |

임베딩 벡터는 런타임 저장소의 구현 세부사항이므로 교환 계약에 포함하지 않는다.

### RetrievedChunk

Retriever가 생성 파이프라인에 넘기는 검색 결과다.

| 필드 | 필수 | 설명 |
| --- | --- | --- |
| `query_id` | 예 | 요청 추적 ID |
| `chunk` | 예 | 검색된 `Chunk` |
| `rank` | 예 | 해당 검색 결과 순위 |
| `score` | 예 | 검색 점수. 해석을 위해 `score_type`과 함께 기록 |
| `score_type` | 예 | similarity, distance 등 점수 의미 |
| `retriever_version` | 예 | 재현에 필요한 검색기·설정 버전 |
| `index_name` | 예 | 결과가 나온 논리 인덱스 |

서로 다른 논리 인덱스나 모델의 점수를 직접 같은 척도로 간주하지 않는다. 양쪽 인덱스 결과의 병합 방식은 Dev set으로 결정한다.

### EvidenceCheckResult

역할표의 C 담당 법령 후보 연계·근거 점검 노드가 D/E 통합 파이프라인에 넘길 **2차 인터페이스 후보**다. 점검할 주장 단위와 직렬화 형식은 미결정이며, 다음 필드는 최소 초안이다. 법령 목록 chunk는 명칭·유형·기관·날짜 같은 목록 주장만 점검할 수 있고 조문 또는 법률 해석 주장을 `supported`로 판정할 수 없다.

참조 구현의 실행 가능한 법령 근거 capability는 `legal_metadata`,
`legal_article_body`, `legal_interpretation`으로 구분한다.
`supported_legal_evidence_aspects(chunks)`는 검증된 `metadata_only` 법령
chunk에서 오직 `legal_metadata`만 도출한다. 요구 capability에
`legal_article_body` 또는 `legal_interpretation`이 하나라도 포함되면 목록
chunk로 충족할 수 없으며, `EvidenceState`와 `decide_abstention`은 이를
`NO_EVIDENCE`로 판정해 반드시 보류한다.

| 필드 | 필수 | 설명 |
| --- | --- | --- |
| `query_id` | 예 | 원 질문과 답변 후보를 연결하는 ID |
| `status` | 예 | `supported`, `partial`, `unsupported`, `conflict`, `not_applicable` 중 하나 |
| `claim_checks` | 예 | 주장 식별자, 판정, 근거 chunk ID와 공개 가능한 사유 목록 |
| `evidence_chunk_ids` | 예 | 점검에 실제 사용한 법령 근거 chunk ID 목록 |
| `checker_version` | 예 | 재현 가능한 점검 규칙·모델 버전 |

이 결과는 최종 정답을 단독 판정하지 않는다. D/E 파이프라인은 검색 근거와 함께 사용하고, `unsupported`나 `conflict`를 근거 보강·답변 수정·보류 신호로 처리한다.

### AnswerResult

생성 파이프라인과 Streamlit이 공유할 결과다.

| 필드 | 필수 | 설명 |
| --- | --- | --- |
| `query_id` | 예 | 요청 추적 ID |
| `answer` | 예 | 공개 가능한 최종 답변. 보류 시 보류 문구 |
| `abstained` | 예 | 근거 부족 등으로 답변을 보류했는지 여부 |
| `abstention_reason` | 조건부 | `no_evidence`, `conflict`, `stale`, `safety` 등 보류 이유 |
| `citations` | 예 | `chunk_id`, 문서명, 위치, 출처 URL 목록 |
| `evidence_chunk_ids` | 예 | 실제 답변 근거로 사용한 검색 chunk ID 목록 |
| `latency_ms` | 예 | 전체 응답 시간 |
| `index_versions` | 예 | 답변에 사용한 데이터·청킹·임베딩 인덱스 버전 목록 |
| `pipeline_version` | 예 | 재현 가능한 파이프라인 설정 버전 |
| `error_code` | 조건부 | 실패 시 공개 가능한 오류 코드 |

인용은 검색되지 않은 chunk를 참조할 수 없다. UI에서 근거 문서를 확인할 수 있도록 문서명, 섹션 위치와 공식 공개 URL을 제공하되, 공개할 수 없는 원문이나 개인정보를 그대로 노출하지 않는다. 법령 인용의 locator는 `기본정보`이고 목록 메타데이터만 뒷받침하며 조문 인용으로 표시하지 않는다.

## 데이터·청킹·인덱싱 설계

### 공통 전처리

1. 계약과 필수 필드를 검증한다.
2. 메뉴·푸터·반복 안내 등 검색을 방해하는 boilerplate를 제거한다.
3. 공백과 문자 표현을 정규화하되 원천 식별자, 날짜, 금액과 자격 조건을 보존한다.
4. `source_id`와 `content_hash`로 완전·근접 중복 후보를 식별한다. 서로 다른 `source_id`의 동일 content는 지역·기관별 별도 서비스일 수 있으므로 자동 제외하지 않고 warning으로 기록한다.
5. 권리 불명확, 민감정보 검토 미완료와 치명적 파싱 오류 문서를 격리하고 검토 결과를 기록한다. `metadata_only` 법령의 본문·조문 미포함은 격리 또는 warning 사유가 아니다.
6. 구조 기반 청킹 후 `Chunk` 계약과 인용 위치를 검증한다.

인수 보고서의 `issues`는 전체 인수를 거부하는 blocking 오류이고, `warnings`는 중복 후보나 권장 섹션 누락을 관측하되 인수를 막지 않는 non-blocking 진단이다.

제외된 문서는 이유와 건수만 공개 가능한 범위에서 기록하며 조용히 누락하지 않는다.

### 출처별 구조 기반 청킹

- 보조금 문서는 한 서비스·사업을 부모 문서로 유지하고 지원 대상, 지원 내용, 신청 기간, 신청 방법과 문의처 같은 섹션 경계를 우선한다. chunk prefix에 정규 지역명을 넣어 의미 검색에서도 지역 문맥을 보존한다. 원천에 신청 방법이 없으면 누락을 warning으로 남기되 지원 대상과 지원 내용이 보존된 문서는 인수한다.
- 법령 문서는 목록 레코드 하나를 부모 문서로 유지하고 `기본정보` 단일 섹션을 청킹한다. chunk에는 법령명, 원천 유형과 정규화 목록 metadata를 포함해 단독 검색돼도 명칭·기관·날짜 문맥을 잃지 않게 한다. 조·항·호·목 경계나 본문은 생성하지 않는다.
- 하나의 구조 단위가 모델 입력 한도를 넘을 때만 재귀 분할을 적용한다. 짧은 인접 단위 병합과 overlap은 출처별 규칙으로 관리한다.
- `800자`, `overlap 100자`와 LangChain 재귀 분할기는 **Baseline 후보일 뿐 확정값이 아니다.** 샘플 길이 분포와 Dev 검색 결과로 결정한다.

### 논리 인덱스 분리 제안

보조금과 법령은 문서 구조, 최신성, 인용 위치와 질문 의도가 다르므로 `subsidy`와 `law` 논리 인덱스를 분리하는 안을 제안한다. 단일 인덱스와의 장단점을 확인해 Gate 2 구현 전에 팀이 승인할 항목이며, 승인 전에는 공통 계약의 확정 조건으로 취급하지 않는다. 분리안을 선택해도 물리적으로 같은 Vector DB의 collection·namespace 또는 이에 준하는 경계를 사용할 수 있다.

- 인덱스 버전은 데이터, schema, 청킹과 임베딩 설정 식별자를 포함한다.
- 설정이 바뀌면 기존 Baseline을 덮어쓰지 않고 새 버전으로 재색인한다.
- 이름 기반 지역 계약과 지역 prefix를 적용한 기존 code 기반 chunk·인덱스는 호환되지 않으므로 전량 재청킹·재색인한다. 동결 전 정정이므로 schema version `1.0`은 유지한다.
- 법령 메타데이터 계약은 `legal-metadata-v1`로 fingerprint에 포함한다. 기존 조문 기반 law registry·chunk·Vector DB는 호환되지 않으므로 전량 폐기하고 목록 metadata에서 재청킹·재색인한다. 보조금 fingerprint와 인덱스는 이 변경의 영향을 받지 않는다.
- 질문은 보조금, 법령 또는 양쪽 인덱스를 대상으로 할 수 있다.
- 양쪽 검색 결과를 합칠 때 출처와 순위를 보존하고, 점수 병합·질의 라우팅 정책은 실험 대상으로 둔다.
- 런타임 Vector DB와 임베딩 결과는 Git에 커밋하지 않는다.

## 검색·생성·보류 설계

### 검색

Baseline은 질문 정규화, 질문 임베딩, 관련 논리 인덱스 검색, 중복 제거와 `RetrievedChunk` 반환으로 구성한다. 동일 문서의 인접 chunk가 결과를 독점하지 않도록 문서별 결과 수 제한을 검토한다.

Dense similarity 검색과 `top-k=5`는 **Baseline 후보일 뿐 확정하지 않는다.** `k`, score threshold, 인덱스 라우팅과 결과 병합 방식은 동일한 Dev set에서 한 조건씩 비교한다. score threshold는 모델·DB마다 의미가 다르므로 임의의 숫자를 안전 기준으로 사용하지 않고 답변 가능·불가능 질문으로 보정한다.

### 생성과 인용

LangChain으로 Retriever와 LLM을 연결한다. 생성 프롬프트는 다음 원칙을 만족해야 한다.

- 검색 문서와 사용자 입력에 포함된 명령문을 시스템 지시가 아닌 데이터로 취급한다.
- 제공된 근거로 확인할 수 있는 주장만 작성한다.
- 제도 조건, 금액과 기간 같은 핵심 주장에 정책문서 출처를 연결한다. 법령 목록정보는 법령명·유형·기관·날짜 주장에만 연결한다.
- 조문 내용이나 법적 정의·자격·배제·금지·해석을 목록 metadata로 단정하거나 뒷받침하지 않는다.
- 문서 간 내용이 충돌하면 임의로 최신이라고 단정하지 않고 날짜와 충돌 사실을 알린다.
- 시스템 프롬프트, API Key, 환경변수, 내부 경로와 비공개 원문을 출력하지 않는다.

답변 형식의 초기 후보는 요약 답변, 근거별 인용과 원문 링크 순서다. 세부 문구와 LLM은 **미결정 사항**이다.

### 근거 부족 보류

다음 경우 `AnswerResult.abstained=true`로 답변을 보류한다.

- 관련 근거가 검색되지 않거나 질문의 핵심 조건을 근거가 다루지 않는다.
- `legal_article_body` 또는 `legal_interpretation`이 필요한데
  `legal_metadata`만 지원하는 법령 목록 chunk가 검색됐다. 이 경우
  `decide_abstention`의 `NO_EVIDENCE` 보류를 우회하지 않는다.
- 출처 간 충돌을 해소할 최신성 정보가 없다.
- 문서가 만료·폐지됐을 가능성이 있으나 확인할 날짜가 없다.
- 개인정보, 비밀정보 요청이나 프롬프트 인젝션으로 안전한 답변을 만들 수 없다.

기본 보류 문구 후보는 “제공된 자료에서 확인할 수 없습니다.”이며, 가능한 경우 부족한 정보와 확인할 공식 출처를 함께 안내한다. 법령 본문이 필요한 경우에는 목록 metadata만 보유한다는 한계와 국가법령정보센터 공식 상세 페이지를 안내한다. score 하나만으로 보류하지 않고 근거 존재, 질문 충족도, 충돌과 최신성을 함께 평가한다.

파이프라인 오류는 근거를 정상적으로 평가한 보류와 구분한다. 오류 시 공개 가능한 오류 안내와 `error_code`를 반환하고, 보류 지표가 아니라 오류율에 집계한다.

## Baseline 후보와 미결정 사항

다음 표의 후보는 구현 착수점을 비교하기 위한 것이며 팀 승인 전 확정 설정으로 취급하지 않는다.

| 항목 | Baseline 후보 | 미결정·확인 사항 |
| --- | --- | --- |
| 교환 형식 | JSONL + JSON Schema | 파일·API 전달 방식, schema version 정책 |
| Loader | 출처별 정규화 결과를 LangChain Document로 변환 | 실제 수집 결과 형태와 오류 처리 |
| Splitter | 구조 우선, 재귀 분할 fallback | 길이 단위, 병합, `800자/100자 overlap` 후보 검증 |
| Embedding | 한국어 복지 문서와 법령 목록정보를 지원하는 단일 모델 | 모델명, 차원, 비용, 로컬·API 환경 |
| Vector DB | Chroma | 운영 환경, metadata filter, 영속성, FAISS 등 대안 |
| 인덱스 구성 | 출처별 2개 논리 인덱스 | 단일·분리 구성, 버전 경계와 결과 병합 방식 |
| 검색 | dense similarity | 거리 함수, `top-k=5` 후보, threshold, 양쪽 인덱스 병합 |
| 생성 | 근거 제한 프롬프트를 사용하는 단일 LLM | 모델명, 비용, 지연 시간, 구조화 출력 지원 |
| 인용 | 문서명 + 섹션 + 공식 상세 URL | 화면 표현, 유형별 직접 링크와 목록근거 한계 표시 방식 |
| 보류 | 근거 부족·충돌·최신성·안전 사유 분류 | 판단 규칙과 임계값 |

모델과 저장소 선택 시 한국어 검색 품질, 메타데이터 필터, 재현성, 비용, 응답 시간과 새 환경에서의 실행 가능성을 함께 비교한다. 외부 API 후보는 사용자 입력·검색 문서의 보존, 학습 사용 여부와 전송 조건도 확인한다.

## 평가와 실험 계획

### 평가 세트

- Dev set은 개발 중 반복 평가하고 Holdout set은 최종 설정 확정 뒤 Gate 6에서 한 번만 사용한다.
- 두 세트의 질문과 정답 근거는 첫 Baseline 실행 전에 동결하고 경로, 버전과 가능한 경우 hash를 기록한다.
- 답변 가능한 질문과 문서에서 답을 찾을 수 없는 질문을 모두 포함한다.
- 보조금 단독, 법령 목록 단독, 두 출처 연결, 조건 누락, 최신성 충돌과 표현을 바꾼 질문을 포함한다.
- 조문·법률 해석 질문을 답변 불가 사례에 포함해 보류와 공식 원문 안내가 작동하는지 평가한다.
- 질문별 정답 근거에는 `doc_id`, `chunk_id` 또는 원문 위치를 기록한다.
- Holdout 결과를 본 뒤 설정을 다시 튜닝하지 않는다.

평가 질문 수와 유형별 비율은 **미결정 사항**이다. Dev·Holdout의 답변 가능·불가능 질문을 충분히 포함하도록 팀이 데이터 규모에 맞춰 확정한다.

### 지표와 수용 기준

지표별 분모, 판정 rubric, 평가자 수와 오류 집계 규칙은 첫 Baseline 실행 전에 문서화해 동결한다. 아래 수치는 확정 기준이 아니라 그 합의를 위한 초기 제안값이다.

| 영역 | 지표 | 초기 제안값/팀 합의 필요 |
| --- | --- | --- |
| 검색 | Recall@k | `Recall@5 ≥ 0.85`는 초기 제안값이며 팀 합의 필요 |
| 검색 | MRR@k, 정답 문서·chunk 적중률 | 수용 기준은 팀 합의 필요 |
| 답변 | 근거 일치도·정답성 | `근거 일치도 ≥ 0.90`은 초기 제안값이며 팀 합의 필요 |
| 인용 | citation precision·coverage·URL 유효성 | `citation precision ≥ 0.95`는 초기 제안값이며 팀 합의 필요 |
| 보류 | 답변 불가 질문 precision·recall | `보류 recall ≥ 0.90`은 초기 제안값이며 팀 합의 필요 |
| 운영 | p50·p95 응답 시간 | 모델·환경 확인 후 초기 제안값을 정하고 팀 합의 필요 |
| 안정성 | 오류율 | `오류율 ≤ 0.02`는 초기 제안값이며 팀 합의 필요 |
| 데이터 계약 | 필수 필드 검증·실패 기록률 | 승인된 샘플의 필수 필드 충족률 100%, 실패 기록률 100% |
| 안전성 | 인젝션·비밀정보 노출 시나리오 | 합의한 시나리오에서 비밀값·시스템 프롬프트 노출 0건 |

자동 지표만으로 답변 품질을 확정하지 않는다. 평가 기준표에 따라 사람이 근거 일치, 누락, 과잉 단정과 인용 위치를 확인하고 판정 근거를 남긴다.

### 실험 규칙

1. 첫 실행 결과를 Baseline으로 보존한다.
2. 같은 Dev set, 데이터와 나머지 설정을 유지하고 한 실험에서 한 조건만 바꾼다.
3. 청킹 길이, overlap, `k`, embedding, 검색 방식과 프롬프트를 동시에 바꾸지 않는다.
4. 질문별 질문 ID, 문서·chunk ID, 점수, 지표, 응답 시간, 오류와 공개 가능한 답변을 저장한다.
5. 성공 평균뿐 아니라 실패 질문과 실패 유형을 기록한다.
6. 데이터·청킹·평가 조건 변경 시 버전과 설명을 갱신하고 기존 결과를 덮어쓰지 않는다.
7. 최종 설정을 확정한 뒤에만 Holdout을 실행한다.

## 보안·개인정보·최신성

### 보안과 개인정보

- 공개가 허용된 샘플 문서만 저장소에 포함한다.
- 법령·행정규칙·자치법규의 본문·조문은 수집 산출물, fixture와 Vector DB에 포함하지 않는다.
- 전체 생성 JSONL과 원천 응답은 런타임 산출물로 Git에서 제외하고, 대표 샘플과 manifest·Document Card만 추적한다.
- API Key, 환경변수 값, 개인정보, 내부 원문과 런타임 Vector DB를 커밋하지 않는다.
- 추후 만드는 환경변수 예시 파일에는 변수 이름과 비밀이 아닌 설명만 두고 실제 값을 넣지 않는다.
- 개인정보·민감정보 검사 상태가 미확인인 문서는 색인을 보류한다. 검출된 문서는 공개 정보 여부와 목적 적합성을 검토해 마스킹·제외·허용 중 하나를 기록한다.
- 사용자 입력과 검색 문서는 명령이 아니라 데이터로 취급한다.
- 로그에는 질문 ID, 문서·chunk ID, 지표와 공개 가능한 결과만 남기며 원문 질문, 시스템 프롬프트, 개인정보, 내부 원문과 비밀값을 남기지 않는다.
- 원문 URL과 라이선스 상태를 검증하고 이용 조건이 불명확한 문서는 제외한다.
- 출처 링크는 허용한 공식 도메인인지 검증하고, 문서·모델이 만든 HTML이나 Markdown을 UI에서 신뢰해 그대로 실행하지 않는다.
- 오류 메시지는 내부 경로, 원문과 비밀정보를 노출하지 않는 코드로 반환한다.

### 최신성

- `collected_at`, `source_updated_at`, `effective_from`, `effective_to`를 가능한 범위에서 보존한다.
- 법령 개정판과 보조금 서비스 변경판을 같은 문서로 덮어쓰지 않고 버전 관계를 유지한다.
- 만료·폐지 문서는 검색 제외 또는 명시적 경고 중 하나를 정책으로 정한다.
- 동일 제도·법령의 충돌 결과가 검색되면 최신 버전을 판단할 충분한 메타데이터가 있는지 먼저 확인한다.
- 수집 갱신주기와 재색인 주기는 A/B/C가 제공한 출처 특성을 바탕으로 팀이 결정한다.
